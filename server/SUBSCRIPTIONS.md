# Subscription and payment configuration

The API uses `APP_MODE` and `MONGODB_DB_NAME` together. Startup rejects a mismatch:

| APP_MODE | MONGODB_DB_NAME | Razorpay mode |
| --- | --- | --- |
| `development` | `digital_khata_development` | Test (`rzp_test_…`) |
| `testing` | `digital_khata_testing` | Test (`rzp_test_…`) |
| `production` | `digital_khata_production` | Live (`rzp_live_…`) |

The checked-in `server/.env.example` is development-only. Set environment values in an untracked environment file or deployment secret store; do not copy production credentials into a developer machine.

## Checkout safety

`RAZORPAY_CHECKOUT_ENABLED` defaults to `false`. Do not enable it until the Android distribution route and billing eligibility are confirmed and a supported native checkout integration is present. Production also requires `ANDROID_BILLING_POLICY_CONFIRMED=true` as an explicit deployment decision. The current Expo app has no Razorpay native checkout SDK and intentionally keeps its payment button disabled. No hidden URL or WebView flow is used.

The server-side order and verification API is behind that flag. Configure `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, a per-environment `RAZORPAY_WEBHOOK_SECRET`, and a public HTTPS `RAZORPAY_WEBHOOK_URL` ending in `/api/v1/payments/webhook` only in the backend secret store. Test application modes accept only test key IDs; production accepts only live key IDs. Checkout stays unavailable if credentials are missing or do not match the mode.

Razorpay webhooks use the raw request body and `X-Razorpay-Signature`; deduplication uses `X-Razorpay-Event-Id`. Configure separate webhook URLs and secrets per environment. Create MongoDB indexes before enabling the payment endpoints with `cd server && npm run indexes`.

## Pricing and tax

Plan seeds are inserted only when a plan code is absent; they do not overwrite later database pricing changes. Prices are integer paise. Discount is rounded to the nearest paise, with half paise rounded upward. `SUBSCRIPTION_TAX_BPS` and `SUBSCRIPTION_TAX_INCLUSIVE` configure the quote calculation; the default is zero tax and exclusive mode. Checkout additionally requires `SUBSCRIPTION_TAX_POLICY_CONFIRMED=true`, so the default cannot be used to collect money before the merchant's tax policy is reviewed. Each payment order persists its purchase-time plan, discount, tax, currency, and amount snapshot.

Subscription months use UTC calendar arithmetic and clamp to the last day of a shorter target month. For example, January 31 plus one month ends February 28 (or 29 in a leap year).

## Plan transitions and refund policy

Same-plan purchases extend the current paid period. Business-to-Pro purchases are scheduled after current Business access ends. A Pro-to-Business immediate upgrade remains unavailable because a safe unused-value/tax credit calculation has not been approved. Refund webhooks update payment history and write an audit event requiring review; they do not silently revoke already-granted access. A future authorized operator workflow must decide any entitlement change.

Free is the computed effective plan whenever no paid period is active. Existing customers and ledgers remain untouched on expiry. Customer creation is protected by a transactional per-shop usage reservation; a limit rejection leaves offline local data and its failed queue record intact while allowing later unrelated queued changes to proceed.

## Notifications and receipts

The mobile app schedules local reminders for 15, 7, 3, and 1 day before expiry and on expiry when notification permission is granted. Android delivery time is subject to OS scheduling. Cached subscription data and payment history use the existing encrypted SQLCipher database. An optional backend worker can use the application's existing Expo Push token/provider path for expiry, payment-success, and payment-failure messages when `SUBSCRIPTION_PUSH_ENABLED=true`; delivery is deduplicated per subscription event. This is not direct FCM integration; the repository has no Firebase Admin configuration or credentials. Gateway references appear in payment history, but tax invoices are not generated by this implementation.
