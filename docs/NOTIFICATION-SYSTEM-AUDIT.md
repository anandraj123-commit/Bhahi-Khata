# Notification system audit

9 November 2026. Source inspection before implementation. No database/provider operations or automated tests.

## Existing architecture
Admin: no notification sidebar, CRUD routes, rich-text editor or CTX implementation. Existing App Router pages require role permissions; same-origin proxy allowlists endpoints, forwards session/CSRF and trusted origin. AdminAudit supports transactional audit writes. Existing ShopSelect/customer-shops and paginated tables are reusable. ADMIN/SUPER_ADMIN have global management permissions; SUPPORT is read-only shops.

Mobile: App.tsx Home bell opens notifications. The screen fetches GET /notifications only while opened, holds at most100 notifications in memory, and patches reads online. It also renders independent local recent-activity audit entries; these must stay. Expo native push registration uses existing Device tokens; Expo Go skips remote registration. Push taps currently handle subscription routes. Subscription reminders have separate local schedules and server push logs. There is no persistent notification cache, read acknowledgement queue or administrative detail screen. Existing SQLCipher SQLite v6 uses SecureStore keys, account-scoped tables and encrypted exclusive transactions; no plaintext fallback is acceptable. Offline authentication lasts up to30 days and is tied to cached account/session. Connectivity observes network/app resume; financial sync queue contains ledger-specific deltas and must not receive arbitrary notification commands.

Backend: Notification -> notifications has shopId, clientId, title, body, read and timestamps. GET lists latest100; PATCH /notifications/read is monotonic and shop-scoped (empty IDs historically marks all). Reminder worker creates inbox records after SMS/WhatsApp delivery. SubscriptionNotificationLog/preferences and subscription reminder worker are independent. Device -> devices binds shop/token; existing sendPush sends Expo batches, tickets are not device receipts. Auth verifies user session version and shop ownership/phone. NotificationRoutes are mounted through existing API routing. There is no administrative campaign, schedule, rich content, per-campaign publication or push-recovery state.

Workers start in server/src/index.js and use node-cron in the existing backend process. Payment workers must not be restarted for development validation. Existing reminder scheduling uses configured timezone; new Admin UI follows UTC convention and stores ISO UTC timestamps.

## Online/offline behavior and gaps
Online inbox fetch/read works only during screen visits; no durable offline inbox. Offline previously cached financial/audit data remains accessible, but server inbox is not cached. Push delivery while closed depends on native OS/provider; no guaranteed offline delivery. Subscription taps exist; administrative taps are absent. Reconnection sync currently handles financial deltas, not inbox state. Logout clears the offline session and may retain encrypted account data; notification UI must clear immediately and scope every asynchronous result to current account. Reads must be monotonic across stale responses and multiple devices.

## Implementation architecture
Add environment-scoped AdminNotification campaigns, retaining existing Notification as per-shop inbox and its legacy fields. Use deterministic per-campaign/shop inbox IDs for idempotency; add bounded server publication with atomic leases, transactional batches and a new opt-in scheduler in the existing backend process. No separate worker process and no automatic production indexes. Recipient identity is validated shop plus owner, not an assumption that a mobile number globally identifies a shop.

Before first publication allow content/recipient/schedule edits with revision checks; after publication freeze targeting/schedule, allow content and visibility updates without resend. Soft deletion is terminal, status=false, with transactional AdminAudit. Recipient/read evidence remains; published inactive campaigns disappear on server reads and offline reconciliation, while encrypted cached evidence remains hidden rather than destroyed.

Store allowlisted rich-document JSON rather than accepting arbitrary HTML. Use maintained Tiptap editor; no CTX dependency was found. Server normalizes supported nodes/marks and safe https/http links, rejects unknown attributes/types and caps size/depth. Render React/React Native nodes without HTML execution.

Extend existing mobile inbox endpoints compatibly with bounded page pagination, unread count, details, and a bounded known-ID reconciliation endpoint for inactive/edited cache entries. Add account-scoped encrypted SQLite inbox plus monotonic durable read acknowledgements; reuse existing database/transaction/connectivity/auth primitives. Keep the financial sync queue unchanged. UI retains recent activity, adds cached administrative details, badge, refresh/load-more, and push taps. In Expo Go/no encrypted storage, online browsing remains possible but offline durability is explicitly unavailable.

Push is optional, inbox authoritative. Reuse registered tokens/provider. Persist claims before sending, record provider ticket acceptance distinctly from delivery, never automatically resend ambiguous outcomes. No notification is marked read by push. No real pushes during validation.

## Risks and deployment boundaries
Transactions require MongoDB replica-set support. Index deployment is explicit and reviewed; no runtime index migration. Atomic IDs protect duplicate publication even before optional query indexes. Push cannot offer exactly-once physical delivery; ambiguous requests must remain reviewable. Native-device acceptance, OS background behavior, offline SQLCipher migration, multiple-device reads, provider tickets and actual scheduling are not established by static builds. Existing retention/session/token-sharing behavior is preserved; new content must never leak on account switches. Rich-text limits and selected-recipient caps must be documented. No production readiness claim.
